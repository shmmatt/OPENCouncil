### #18 - Integer-Based Usage Tracking & Ghost Data Refinements

**What & Why**
The current usage accounting relies on a percentage metric that fails to trigger the 80% soft warning for users with small limits (e.g., 3 guest queries). We need to pivot strictly to predictable integer-based tracking ("Number of Queries"). Additionally, the "Ghost Data" blur cuts off the text too early (~100 chars), failing to provide enough context to hook the reader. Finally, the email input and submit button in the unlock overlay have mismatched widths.

**Done looks like**
* **Predictable Metrics:** Usage endpoints and tracking logic evaluate raw query counts (e.g., `used` and `max`) rather than calculating API weights or arbitrary percentages.
* **UI Status Bar:** The Usage Bar in the header drops the `%` sign. It displays raw integers (e.g., `2 / 3` or `10 / 10`). The visual progress bar width still calculates dynamically via `(used / max) * 100`.
* **Warning States:** The amber soft-warning (`bg-amber-500`) triggers exactly when `max - used === 1` (1 query remaining). The red paywall (`bg-red-500`) triggers when `used >= max`.
* **Extended Teaser:** The `ChatMessageBubble` allows roughly 250 to 300 characters of clear text (about 2-3 lines of context) before applying the CSS blur gradient, giving the user a better hook.
* **Form Polish:** The email `<input>` and "Unlock answer" `<button>` inside the overlay are perfectly aligned to the exact same width (e.g., using `w-full max-w-sm`).

**Out of scope**
* Changing the underlying MapReduce execution limits or backend AI generation.
* Changing the `oc_bypass_credits` cookie logic (keep granting 10 bypass credits on email unlock).
* Modifying the Stripe checkout logic.

* **Task 1: Backend Accounting:** Update the usage tracking endpoint (`/api/auth/usage` or equivalent) to return discrete `used` and `max` integers based on prompt counts. Ensure the `chatV2Route.ts` enforces limits based on these raw integers rather than a percentage.
